# 2026-10-27 · 为什么把这个项目单独开一个工作空间

## 起因
在「文旅导出资产」那边清生产磁盘时发现这台机器上最大的单个文件不是文旅的，而是本站（doupi123.top / Halo）
容器的 json 日志：**723M / 3,753,979 行**，而且没有配轮转。同一台机上跑着 7 个项目，根分区只剩 394M。
用户要求为个人网站单独开一个工作空间来管这些事。

## 这一轮已经确认的事实
| 项 | 读数 | 来源 |
|---|---|---|
| 站点域名解析 | `doupi123.top` / `www.doupi123.top` → **120.26.139.203** | 阿里 DoH（`probe/doh_resolve.py`，绕开本机 fake-ip） |
| 服务器 | `iZbp1b7twrcrxtthptiza7Z`，`/` 40G 用 37G，可用 **394M / 99%** | `probe/ssh_sample.py` |
| 容器 | 6 个在跑：`1Panel-halo-UaWD`、`1Panel-mysql-H38k`、`1Panel-redis-KbyG`、`1Panel-obsidian_livesync-WJYC`、`1Panel-openresty-qKv1`、`fast-note-sync-service` | 同上 |
| Halo | 镜像 `halohub/halo-pro:2.25.4`，2026-08-20 04:01 UTC 起一直运行 | `docker inspect` |
| 日志 | `/var/lib/docker/containers/38e4ec56…/…-json.log` **723M**，驱动 `json-file`，**无 max-size** | `du` / `docker info` |
| 日志开头 | 若干 `|-WARN in c.q.l.core.rolling.SizeAndTimeBasedRollingPolicy@…`（logback 滚动策略告警） | `head -1` |
| 日志末行 | `2026-10-27T11:40:15.519+08:00 INFO 1 --- [tor-tcp-epoll-3] run.halo.app…` | `tail -1` |

换个增长率的算法：2026-08-20 → 10-27 共 **68 天**，723M ⇒ **约 10.6M/天**，是文旅那边正常日增（~31M/天全机）
里最大的一块来源之一。

## 还没查明 / 没动手的
1. **为什么一天长 10M** —— 我试过 `tail -n 20000` 抽样归类，但 723M 的文件在 SSH 上取 2 万行太慢（>10 分钟，
   被我 kill 了）。下次换更轻的办法：`tail -c 2000000`（只取尾部 2MB）+ 按日志格式解析；
   或者直接在容器里 `docker logs --tail 500 1Panel-halo-UaWD` 看，避开读整文件。
2. **是否截断** —— 没做，等用户确认（截断会丢历史日志，但 723M 的历史日志价值本来就低）。
3. **是否开轮转** —— 需要改 `/etc/docker/daemon.json` 并 `systemctl restart docker`，
   这会**重启这台机上所有容器**（含文旅依赖的 openresty 与 MySQL），必须挑时间窗并确认文旅那边不再发布。
4. **Halo 自己的日志**：`/opt/1panel/apps/halo/…` 下应该还有 logback 自己写的文件（`logs/` 目录），
   这次只看了 docker 的 json 日志，没看 Halo 应用日志目录 —— 下次一起量。

## 下次开工的第一组命令（只读）
```bash
df -h /; du -sm /opt/1panel/apps/halo/* 2>/dev/null | sort -rn | head
ls -lh /opt/1panel/apps/halo/*/logs 2>/dev/null | head
du -sm /var/lib/docker/containers/*/*-json.log | sort -rn | head -5
docker inspect 1Panel-halo-UaWD --format '{{.HostConfig.LogConfig}}'
tail -c 300000 /var/lib/docker/containers/38e4ec56*/38e4ec56*-json.log | tail -50
```
