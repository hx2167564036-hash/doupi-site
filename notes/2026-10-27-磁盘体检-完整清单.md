## 四、日志为什么还在长（723M/3,753,979 行，约 10.6M/天）

抽尾部 3MB 看，**不是正常的访问日志，是一个死循环的报错**：

- 3MB 里 **134 次**：`SinglePageReconciler` 的 worker 反复 abort 后 re-enqueue
  ```
  run.halo.app.infra.utils.JsonParseException: com.fasterxml.jackson.core.JsonParseException:
  Unexpected character ('<' (code 60)): expected a valid value (JSON String, Number, Array, Object ...)
      at run.halo.app.extension.controller.DefaultController$Worker.run(DefaultController.java:174)
  ```
  ⇒ 某一条「独立页面 / 扩展数据」里存的是 HTML（以 `<` 开头），代码按 JSON 解析，每次都炸、然后重新入队，
  **每 ~20 秒一次，每次一整个 Java 堆栈**，这就是 10M/天的来源。
- 另有 40 次 `io.netty.handler.timeout.ReadTimeoutException`、12 次 `InvalidLineSeparatorException`，
  来自 `66.132.172.188` 这类外部扫描/探测的坏请求（噪音，占比小）。
- 抽样里还出现 **1 次 `java.lang.OutOfMemoryError`** —— 2G 内存 + 1.6G 堆的机器上，值得留意。

坑（记下来免得再踩）：
- `journalctl --vacuum-size=20M` **对活动日志无效**（报 `freed 0B`），必须先 `journalctl --rotate` 把活动文件轮转成归档，再 vacuum。
